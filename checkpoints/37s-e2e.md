## What was added

ONE new row to the existing registered-pair X-flow (the invite match that
`X10` plays to a scholar's mate):

> **37D registered-pair game: drag-on-own-square cancels silently (no server
> REJECTED, no shake) + white capture strip shows a board-derived black
> (`.cap-dark`) glyph, no light**

It covers both contract-37 behavior fixes from a single row (two halves):

- **Half A — silent return-drop.** On the WHITE page, before any capture,
  drag a white piece (the e2 pawn) out a few px and release ON its own square
  (the origin pixel). `completeDrag()`'s `to === from` branch calls
  `releaseGrab()` and returns **before** `socket.emit('move', …)`, so the
  server never logs `move: REJECTED` for it and the canvas is never given the
  `shake` class. The row asserts:
  - no new `move: REJECTED` line in the server log after the drop
    (delta of the TOTAL REJECTED count — the drop is on the invite match, not
    the guest `matchId`, so the guest-scoped helpers can't be used here);
  - the canvas did NOT get the `shake` class within ~500 ms (`cnv.className` /
    `classList.contains('shake')` check);
  - the piece is still on e2 (`board[6][4] & 0b1111 === 1`, a white pawn).

- **Half B — board-derived captured strip.** The white viewer's capture strip
  (`#captured-white`; for `my_color === white` that element renders the pieces
  captured BY white = black pieces, each as `<span class="cap-piece cap-dark">`
  per `renderCapturedPieces()` in `game.js`) must, after white's first black
  capture, contain a black glyph (`.cap-piece.cap-dark`) and NO `.cap-piece.cap-light`.
  In the scholar's-mate line the ONLY black piece white captures is the f7
  pawn (`6.Qxf7#` — the rook stays on a8/h8), so the expectation is exactly
  **ONE `.cap-drop-dark` and ZERO `.cap-drop-light`**.

## How the strip is read (the tricky part)

`renderCapturedPieces()` re-derives the strip from the LIVE `board` every 10 ms
and rewrites it to empty until a black piece is captured. The end modal's reveal
(`showReplay → applyReplayPosition(0)`) then resets the live `board` to the
START position, and a late `validated` event overwrote `__lastValidatedRaw` with
that same start board — so reading the strip from the live board or from
`__lastValidatedRaw` *after* game-end gives the START position (all 8 black pawns
present → 16 "missing" → 16 cap-dark), which is wrong.

Solution: a `MutationObserver` is armed on the white page's `#captured-white`
**pre-start** (in the same pre-block as half A, before `X10`'s move loop). On
the first change that introduces a `.cap-piece.cap-dark` span — the first black
capture — it latches into `window.__strip37`:
- `latched = { dark, light, domDark, domLight }` — the rendered DOM counts
  (`.cap-piece.cap-dark` / `.cap-piece.cap-light`), which are the reliable
  signal (the strip stays non-empty through the replay board-reset until the
  next render tick);
- `derivedDark`/`derivedLight` — an independent recount of the live board using
  the same expected-vs-present logic `renderCapturedPieces` uses (kept as a
  diagnostic; it can read the replay-reset start board if the `validated` and
  `replay` packets were batched in one task, hence the DOM counts are what the
  PASS condition is keyed on);
- `glyph` + `raw` — the captured span's glyph and the strip's innerHTML, for
  the evidence detail.

The 37D row then reads `window.__strip37` (frozen at the capture instant, immune
to the later replay reset) and asserts `domDark === 1 && domLight === 0`.

## Sequencing (the task's documented option)

Sequencing the return-drop mid/late-game is fragile (the mover-turn flag flips
and the board is in flux), so **half A runs pre-start** on the same seated
private invite match (before `X10`'s loop). Half A's silent cancel leaves the
board at the start position, so `X10`'s loop then drives the full scholar's mate
from a clean slate. Half B's latch (armed in the same pre-block) fires when the
loop reaches `6.Qxf7#`. If the known X10/X11 mover-turn load flake aborts the
loop before that move, the latch never fires and the row reports it (the row is
independent of X10's *profile-fetch* logic, so it is only coupled to the mover
turn).
